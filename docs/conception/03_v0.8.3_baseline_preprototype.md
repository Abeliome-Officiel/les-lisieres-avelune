# v0.8.3 — Baseline de conception pré-prototype

Date de consolidation : 4 août 2026.

Périmètre conceptuel couvert : décisions prises jusqu'au 2 août 2026 inclus.

Le travail commencé le 3 août 2026 sur la spécification détaillée du prototype
logiciel est volontairement exclu.

Cette version est la référence de conception à utiliser pour reprendre le cycle
v0.9 du prototype.

---

# 1. Intention générale

Les Lisières d'Avelune est un jeu de gestion, évolution et interaction dans un
monde persistant partagé.

Le jeu doit préserver :

- la créativité ;
- l'onirisme ;
- une écriture littéraire et évocatrice ;
- l'accessibilité ;
- l'inclusivité ;
- l'absence de PvP destructeur ;
- l'absence de classement global humiliant ;
- une progression qui accepte les changements de direction ;
- des échecs produisant de nouvelles situations plutôt qu'une simple
  invalidation de l'investissement.

La cohérence fictionnelle prime sur l'ajout de mécaniques sans justification.

Une mécanique peut cependant produire des valeurs numériques et des
modificateurs lorsque ceux-ci servent la lisibilité et l'équilibrage.

---

# 2. Corcite

Le Corcite est l'unité centrale.

Les trois axes décrivent le même être :

- RPG : identité, pensée, évolution, connaissance, relations ;
- TF : fonctionnement, besoins, production, réseaux et infrastructures ;
- TD : interaction défensive et transformatrice avec les vagues.

Toute mécanique majeure doit préciser son effet sur cet état commun.

---

# 3. Monde

Le monde est partagé.

La Fracture, les vagues, la Lisière, les régions et les Corcites forment un
système persistant.

Les régions ne sont pas conçues comme des consommables disparaissant au fur et à
mesure de la progression.

Les transformations durables peuvent laisser :

- Traces ;
- Échos ;
- cicatrices ;
- modifications du terrain ;
- connaissances.

Les expansions significatives appartiennent plutôt à des chapitres, saisons,
époques ou versions de contenu qu'à une croissance infinie et immédiate.

---

# 4. TD

Référence : v0.8.1.

Points structurants :

- défense globale du Corcite ;
- traitement interne de la vague ;
- composition initiale simple pour le premier test ;
- réduction de puissance et d'effets ;
- captation équitable ;
- modes automatique et manuel ;
- socle commun de tours ;
- variantes liées aux systèmes transversaux ;
- journalisation suffisante pour analyser l'équilibrage.

---

# 5. TF

Référence : v0.8.1.

Points structurants :

- organisme vivant plutôt qu'usine abstraite ;
- besoins et production réunis ;
- stockage par bâtiment ;
- réseaux et connexions significatives ;
- tampons automatiques lorsque nécessaire ;
- répartition ou priorité aux bifurcations ;
- énergie avec capacité et réserve ;
- entretien global ;
- automatique viable mais non optimal ;
- manuel potentiellement plus efficace mais plus exigeant.

---

# 6. RPG

Références : v0.8.1 et v0.8.2.

Le RPG n'est pas une succession d'ordres imposés.

Il rassemble :

- identité ;
- race ;
- classe ;
- métier ;
- mues ;
- compétences ;
- Érudition ;
- recherches ;
- connaissances ;
- relations ;
- mémoire ;
- choix narratifs ;
- accès et déblocages.

Les choix narratifs peuvent avoir des conséquences mécaniques.

---

# 7. Progression

La progression n'utilise pas obligatoirement un niveau global unique.

Elle peut être distribuée entre :

- capacités ;
- éléments de classe ;
- métier ;
- compétences ;
- connaissances ;
- structures ;
- mues ;
- relations au monde.

Le joueur doit pouvoir réorienter son Corcite sans devoir systématiquement
recommencer depuis zéro.

Une réorientation peut cependant demander du temps ou des ressources afin que
les choix conservent un poids réel.

---

# 8. Connaissance

La connaissance du monde peut provenir :

- de recherches ;
- d'observations ;
- de découvertes ;
- de mémoire collective.

Lorsqu'une connaissance devient mondiale, elle est accessible à tous les
Corcites sans attribution individuelle publique.

Les capacités propres d'un Corcite peuvent limiter son interprétation ou son
exploitation.

---

# 9. Social

La coopération doit apporter des possibilités sans transformer les autres
joueurs en dépendances obligatoires permanentes.

Le jeu doit permettre :

- autonomie ;
- entraide ;
- échanges ;
- projets collectifs ;
- contributions au monde.

Le premier prototype n'a pas besoin d'un forum ou d'un chat intégré.

Les outils sociaux plus complexes appartiennent à des phases ultérieures.

---

# 10. Dormance

La dormance suspend le Corcite et ses liens plutôt que de lui assurer une
production passive minimale.

Les personnes affectées par la rupture d'un lien doivent pouvoir en être
informées.

---

# 11. Accessibilité

L'accessibilité doit être intégrée à la conception et non ajoutée après coup.

Les vérifications doivent notamment porter sur :

- surcharge visuelle ;
- surcharge sonore ;
- quantité de texte ;
- rythme ;
- signaux multiples ;
- lisibilité ;
- personnalisation ;
- assistance adaptable ;
- compatibilité avec différents modes d'attention et de traitement de
  l'information.

L'assistance doit rester aussi discrète que possible tout en permettant la
compréhension.

---

# 12. Gouvernance de conception

Le développement conceptuel suit des lots courts.

Format de travail privilégié :

- environ 5 à 8 questions par lot ;
- synthèse avant de poursuivre ;
- éviter les séries dépassant environ 20 questions sans consolidation.

Chaque élément peut recevoir un statut :

- Acté ;
- Déduit ;
- Proposé ;
- Ouvert ;
- Remisé ;
- Hors périmètre.

La conception doit conserver :

- un journal des décisions ;
- un journal des deltas ;
- la distinction entre socle et idées futures ;
- les critères de sortie des phases ;
- des livrables lisibles par un humain ;
- des structures exploitables techniquement.

Une décision actée ne doit pas être rouverte sans motif identifiable.

---

# 13. Frontière du prototype

La v0.8.3 ne définit pas encore l'implémentation finale du prototype logiciel.

Elle définit les contraintes que celui-ci doit respecter.

En particulier, le prototype v0.9 ne doit pas reprendre automatiquement comme
vérité des simplifications anciennes lorsque celles-ci ont été remplacées dans
v0.8.1 ou v0.8.2.

Exemple majeur :

**la limitation systématique à un ordre TD, un ordre TF et un ordre RPG par tour
est obsolète.**

Le prototype doit tester les mécanismes réels suffisamment tôt pour révéler :

- incohérences ;
- boucles trop lentes ;
- boucles dominantes ;
- dépendances inutiles ;
- ressources redondantes ;
- problèmes de lisibilité ;
- difficultés d'équilibrage ;
- défauts d'interaction entre TD, TF et RPG.

---

# 14. Éléments encore ouverts

La baseline ne prétend pas figer :

- toutes les valeurs numériques ;
- toutes les ressources ;
- toutes les tours ;
- toutes les recettes ;
- toutes les classes ;
- toutes les compétences ;
- le nombre final de mues ;
- la cadence définitive des événements ;
- les paramètres définitifs de dormance ;
- la structure commerciale avancée ;
- les interactions sociales avancées ;
- l'ensemble des extensions du monde.

Ces éléments doivent être déterminés par besoin réel, prototypage et
équilibrage plutôt que par remplissage théorique.

---

# 15. Statut

La v0.8.3 constitue la dernière baseline de conception avant reprise du
prototype logiciel v0.9.

Elle doit être utilisée lors de la revue du code et de la documentation
v0.9-dev afin d'identifier les règles héritées de v0.8 devenues obsolètes.
