# PROTO-0.2 — Run de ce soir (3 à 5 h)

## Résultat attendu

À la fin du run, privilégier une **alpha réellement jouable** permettant au concepteur de tester la nouvelle ergonomie. Ne pas viser une finition de sortie officielle.

## Budget de temps indicatif

### 0–30 min — inspection et plan interne
- état Git ;
- architecture ;
- moteurs existants ;
- tests ;
- stratégie minimale de modification ;
- identification des zones de risque.

Ne pas produire un long rapport avant de coder : le diagnostic doit servir directement à l’exécution.

### 30–150 min — cœur fonctionnel
Priorité :
1. énergie simple ;
2. états fonction/population ;
3. bandeaux ressources/capacités ;
4. nœuds productifs ;
5. connexions visuelles naturelles ;
6. évolution/RPG visible avec breakdown des bonus.

### 150–230 min — boucle complète
- défense plus directe ;
- onde sans calendrier gratuit ;
- persistance locale si non faite ;
- assemblage du parcours.

### 230–300 min — stabilisation
- tests ;
- corrections ;
- build ;
- smoke test ;
- petits défauts d’ergonomie évidents ;
- rapport de fin.

Les durées sont indicatives. Ne pas sacrifier une brique essentielle pour respecter artificiellement le découpage.

## Si le temps devient court

Conserver impérativement :
- production/réseau visible ;
- RPG visible et impactant ;
- défense jouable ;
- onde fonctionnelle ;
- énergie sans réserve ;
- population compréhensible.

Reporter avant cela :
- animation ;
- polish visuel ;
- questionnaire intégré ;
- E2E exhaustif ;
- fin de run sophistiquée ;
- drag partout si une alternative clic/tap propre est déjà livrée.

## Si le cœur est terminé en avance

Utiliser le temps restant dans cet ordre :
1. tests des nouvelles primitives ;
2. tactile/mobile ;
3. clavier/accessibilité ;
4. persistance robuste ;
5. fin de run 3 ondes ;
6. E2E minimal ;
7. documentation des composants réutilisables ;
8. amélioration visuelle **uniquement ergonomique** (hiérarchie, états, densité, affordances).

Ne pas inventer du contenu ou des mécaniques pour occuper le temps.

## Checkpoint humain idéal

Le rapport final doit permettre de lancer le jeu immédiatement et de tester sans lire le code.

Le concepteur doit pouvoir fournir des retours sur :
- ce qu’il comprend en premier ;
- ce qu’il cherche ;
- ce qu’il ne voit pas ;
- ce qu’il aime manipuler ;
- ce qui semble artificiel ;
- les choix qu’il perçoit ou ne perçoit pas ;
- la place ressentie de l’évolution/RPG ;
- la qualité de la transition production → défense → onde → adaptation.
